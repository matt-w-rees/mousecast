You are situated inside of an R project source directory. 

The purpose of this project is to integrate data sources and forecast house mouse abundance and plagues in Australian grain growing regions. 
The main management action is to undertake poison-baiting of mice using zinc phosphide (either 25 or 50 dose). 
Providing farmers with early warning of moderate-high or increasing mouse activity is key to help them decide when to bait. 

Mouse data comprises of structured surveys:
a) live-trapping surveys where grids of traps are deployed, usually for 3 or more nights.
b) "rapid assessment" surveys, comprising of active burrow counts (in 100 m transects) and chew card assessments (cards a deployed on same transects, 10 m apart, percentage of card chewed by mice is recorded). 
The same paddock is generally surveyed repeatedly, but there are many cases where another paddock is surveyed instead. 

We also consider citizen observation data of categorical abundance estimates: no, low, moderate of high mouse abundance observed, via the "MouseAlert" website. We consider citizen observation to be less reliable than structured surveys, so often weight it less.

Each survey data type has different detection rates, and mouse detection also likely varies throughout the year for each data type too (namely active burrow counts as soil cracking or dense crop cover can obscure burrows). 

Mice population are generally driven by weather and crop growth patterns. 
It is important to consider there are different cropping schedules across Australia, notably winter-only crop schedule south of Dubbo (approximately) versus summer + winter crops north, in the eastern states. 
Western Australia has winter-only crops, but with slightly different sowing and harvesting dates. 

We consider a crop paddock as a unique "survey site". 
Data sometimes has "site" and "subsite" names, but we use GPS coordinates to determine which paddock the survey was in (although historic data often has coordinates taken from the roadside or a central farm house which makes this challenging, we can use site/subsite names to determine when this is likely the case).
There is also data along fence lines in between paddocks, but we want to discard this data and only keep surveys from within the crop. 
We use the "ePaddock" remotely sensed dataset to determine paddock boundaries, although it is not alway accurate so have to append with hand-drawn paddocks. 

Survey data is currently entered using "ODK" software. Previously "Microsoft Access" was used as the database. Data has also been entered into CSV files, as is MouseAlert data.
ODK Central form definitions (.xlsx, used to build the forms in ODK Central) live in "odk_forms/". Submissions are currently ingested by manually exporting each form from ODK Central ("Export to CSV (with media)") into "raw_data/survey_data/odk/<form_name>.csv/" and reading those files; the live ODK Central API (the "ruODK" package) was used previously but is not currently used.
The "Monitoring" project is the main data source we consider, but we also collate data from an "Ecology" project (live-trap data only in a microsoft access database, mostly experimental studies). Baiting is accounted for explicitly (bait_history/bait_dosage) rather than by excluding treated plots, so both control and treated Ecology data are used. 
There is also additional data sources, such as "GRDC" funded monitoring (via subcontractors). 

This project uses the r-package "targets"; the targets pipeline is "_targets.R" with functions contained within the "r/" folder. It is important to "track" raw files so the pipeline is only re-run (relevant sections of which) when the raw data changes.
When a raw data source is a folder of multiple related files (e.g. an ODK CSV export with main + repeat-group sub-tables), track the whole folder with tar_file(list.files(folder, full.names = TRUE, recursive = TRUE)) and have the downstream read function pick out the files it needs by filename pattern, rather than tracking and passing each file separately.
There is also a "r_not_in_use" folder to store old scripts no longer used, in case they will be useful in the future. 
It is often helpful to review the "r_not_in_use" files when asked to create a new function. 
When a script or function is fully superseded (e.g. replaced by a new approach), move it into "r_not_in_use" rather than deleting it outright. 

The pipeline has two main sections: 
(1) cleaning and combining mouse survey datasets, saving and summarising the resulting dataset through a shiny app for data exploration, as well as a html/pdf simple communication deployed via a website (updated when pushed to github). 
(2) time-series statistical forecast modelling of the cleaned mouse survey dataset, which firstly includes attaching temporally-varying and static covariates to the integrated dataset. 
Section (2) is itself split into lettered pipeline sections in "_targets.R": B) downloads and processes the covariates; C) merges Section A's survey data with Section B's covariates into a seasonal, model-ready panel (one row per paddock x season, framework-agnostic); D) fits and predicts from the forecast model itself, described below.

Section D forecasts mouse plagues with a two-state (plague / not-plague) hidden Markov model, fit with the "hmmTMB" R package, at discrete seasonal time steps matching Section C's paddock x season_year_adj grain. One HMM is fit per paddock, each its own time series via hmmTMB's ID mechanism; Section C's "resolve_survey_visits(mode = 'first')" (r/c_resolve_survey_visits.R) collapses any repeat within-season visits first, so each paddock-season contributes exactly one observation-set. Live-trap count, active-burrow count and chew-card activity enter as three conditionally-independent observation streams given the hidden state, each with its own distribution family (e.g. negative binomial for trap/burrow counts, binomial/proportion for chew-card activity). Most paddock-seasons only have one or two of these three streams (live trapping currently only occurs at a handful of properties; rapid assessment is broader) -- hmmTMB simply drops a missing stream from that time step's likelihood contribution, no imputation needed. 

Transition probabilities (not the observation distributions) are covariate-driven, not paddock-specific, using contemporaneous (current-season) covariate values, not the "_lag1" versions Section C also builds -- the transition itself already relates one season's covariates to the FOLLOWING season's state, so that structure already supplies one season of lag; using "_lag1" on top would silently test a two-season delay instead of the intended one-season delay ("_lag1" stays available for a deliberate two-season-delay test, or for covariates on the observation-distribution side, where there is no equivalent free lag). AE zone enters as a random effect (intercept and slope) on the transition probabilities, which does double duty: partial pooling for estimation, and a diagnostic for whether the covariate-risk relationship is transportable to un-monitored zones -- homogeneous random slopes across monitored zones support applying the pooled relationship nationally; substantial zone-to-zone variation is a warning against it. 

The model is semi-supervised: known plague occurrences anchor the hidden state via hmmTMB's own "state" column mechanism (a value where known, NA elsewhere) rather than being purely latent. A paddock-season is only anchored to the plague state if BOTH: (a) "raw_data/plague_occurrence/yearly_plague_occurrence.csv" flags that paddock's state for the overlapping calendar year(s) -- the conservative, genuinely-declared-plague source; (b) "raw_data/plague_occurrence/regional_mouse_activity_ratings.csv" (built by geocoding every "mouse_updates/*.pdf" report's own named sub-regions onto season_year_adj, then spatially joined to the official GRDC subregion polygon each falls in -- "raw_data/predictor_variables/grdc_regions/growing_subregion/", r/a_attach_grdc_subregion.R) shows a "High" rating for that paddock's own Australian state in that specific season, aggregated up from the underlying grdc_subregion x season ratings (any subregion in the state rated "High" that season counts). Condition (b) matched at grdc_subregion grain originally (roughly 4x finer than ae_zone, a real officially-bounded GRDC layer, closely matching the grain the source reports themselves describe activity at, e.g. "Eyre Peninsula" vs. "Adelaide Plains" as separate assessments within one ae_zone) -- coarsened to the Australian-state grain (2026-08) after confirming this fixed a genuine inconsistency: regional_mouse_activity_ratings.csv only has coverage from its own earliest rated season onward (mouse_updates/ PDFs start Aug 2013), so every earlier season had no possible condition (b) evidence at ANY spatial grain, and an attempt to patch that gap with a state-grain-only fallback used purely pre-coverage produced a rule reading the same regional-ratings source at two different spatial grains depending purely on calendar year -- see r/c_anchor_plague_state.R's "Why state, not grdc_subregion" for the full reasoning. A third condition -- checking the paddock's own raw survey value against a calibrated plague-density threshold -- was tried and dropped: it would anchor using the same result_traps/result_burrow values that also feed the HMM's own observation likelihood, which is circular (see r_not_in_use/c_calibrate_plague_threshold.R and r/c_anchor_plague_state.R for the full reasoning). A plague anchor also propagates forward a few seasons past its trigger (mouse plagues typically outlast one season, though the reports don't pin down the exact season a plague starts or ends), extended further when yearly_plague_occurrence.csv documents a plague spanning multiple consecutive calendar years (a real, recurring pattern, e.g. 2010 and 2011 both flagged for every state), and capped early by any later report showing the state had already dropped to a non-"High" rating. Separately, a paddock-season is anchored to the non-plague state (plague_state = 1) directly whenever regional_mouse_activity_ratings.csv shows at least one "Nil"/"Very Low" subregion rating for that state that season -- specific enough evidence on its own, not propagated the way plague anchors are, since "not currently in plague" is already most seasons' default. Every other paddock-season within regional_mouse_activity_ratings.csv's own coverage is left unanchored (state estimated, not fixed) -- most paddocks in a flagged state/season stay unanchored, since mouse activity is patchy even within a genuine plague year (every report in "mouse_updates/" stresses this). Before that coverage begins (1985 up to the coverage's own earliest season -- the survey panel's own trap-only floor was separately extended back from 2009 to 1985, see below), condition (b) is not just unfavourable but structurally unavailable. Two fallback rules were tried to anchor that stretch from condition (a) alone anyway, and both were reverted (2026-08): a symmetric version (flagged state-year -> plague, unflagged -> non-plague) broke the "yearly_plague_occurrence.csv is too coarse for a negative claim" standard above directly; a positive-only version (respecting that standard) instead produced a genuine near-absorbing-state decode collapse, confirmed live -- ~99-100% of paddock-seasons decoded "plague" across the entire 1985-2002 stretch regardless of whether that specific year was flagged -- the same failure signature as the ae_zone-level degenerate fit below, just showing up as a decode collapse rather than an extreme coefficient. That stretch is therefore left fully unanchored: historic trap survey data still shapes trap_count's own observation distribution, but contributes zero anchor evidence in either direction; see r/c_anchor_plague_state.R for the full detail on both reverted attempts.

A raw-state-CSV-only anchoring rule was also tried (2026-08) -- condition (a) alone, applied across the entire panel with no condition (b) at all -- and reverted the same day: it converged cleanly with plausible coefficients, but anchored 100% of the panel (every paddock has a known state, every year is either flagged or not), turning this from a genuinely semi-supervised model into an essentially fully-supervised one and measurably weakening every observation stream's ability to discriminate the two states (e.g. chewcard_count.prob separation fell from ~1.4%/54% to ~8.6%/20.4%, burrow_count.mean's state1/state2 ratio fell from ~10x to ~1.7x) -- a whole state flagged for a calendar year lumps in many paddocks that were never actually elevated (plague is patchy even within a genuinely flagged state/year, as above), so the field data stops separating the two states as cleanly once anchored at this much coarser grain. The code for that rule and for the (a)+(b) rule above both remain in r/c_anchor_plague_state.R (the (a)+(b) rule is the one actually used).

First pass: fit to every paddock in the four eastern mainland states with regular structured survey data pooled together (fixed-effect-only transitions, no random effect yet), using three transition covariates: rainfall whiplash (12-month sweep = rain_whiplash_trough_to_peak), a 6-month rolling GPP level (gpp_rolling6), and current-season soil moisture (soil_moisture, AWRA level, no whiplash transform -- added 2026-08, both already built/attached in Section B with no new raster work needed). GPP whiplash was separately swept and dropped entirely (see the whiplash-validation section above -- not significant at any of 126 tested combinations); an earlier raw GPP level covariate (a 12-month rolling average) was also dropped from the transition formula (2026-08) after its coefficients repeatedly shrank and flipped sign across earlier iterations of the anchoring rule, a sign it was weakly identified with the available data volume at the time -- gpp_rolling6 revisits this at a shorter (6-month) window alongside soil_moisture rather than alone. rain_whiplash_trough_to_peak and gpp_rolling6 both point the same direction for both transitions (higher values make entering a plague more likely and leaving one less likely); in the first-pass (fixed-effect-only) fit, soil_moisture ran the opposite way for entering plague (wetter conditions less likely to trigger) -- plausible on its own terms (waterlogging/reduced breeding success) but, unlike rain_whiplash_trough_to_peak, not yet checked against real plague-occurrence data, so treated as an untested hypothesis. That sign flips to agree with the other two covariates in the second pass (zone random intercept, below) once "Qld Central" is excluded -- see that paragraph for why, and treat this as a live, evolving finding rather than a settled read. Pooled by Australian state (NSW/VIC/SA/QLD, r/d_build_hmm_data.R's state_filter, 2026-08 -- replaced an ae_zone_filter argument) rather than by ae_zone, specifically to match the grain condition (b) above is itself anchored at -- this changed nothing about which paddocks are actually included (confirmed live: the original 8-AE-zone list already covered every paddock in these 4 states exactly), but some of those zone names genuinely straddle a state border (e.g. "SA Vic Bordertown-Wimmera"), so the old zone-based filter and the state-grain anchor were answering subtly different questions even though the paddock set happened to be identical. Confirmed empirically (2026-08) that a single-zone fit is not viable, even using the zone with the strongest dual-stream overlap ("SA Midnorth-Lower Yorke Eyre"): with the ae_zone-level anchoring design used at the time, every paddock within one zone shared the exact same anchor timing, so the model had zero anchored examples of ever leaving the plague state, and the fit degenerated to a near-absorbing plague state (transition coefficients blowing up to +-50-600 on the logit scale) despite the optimiser reporting formal convergence. Pooling across states resolved most of this; the anchoring rule's own condition (b) has since moved through several grains (ae_zone -> grdc_subregion -> Australian state, described above) as each round of empirical testing surfaced a new blanket-anchoring or evidentiary-inconsistency problem. The survey panel's own trap-only floor was separately extended back from 2009 to 1985 (2026-08) after confirming every historic trap record from 1980 onward had a 100% successful paddock match; that extension measurably worsened trap_count's own pseudo-residuals, and a ~era (historic/modern) detection-side formula tried to fix it was reverted the same day after it drove the historic-era state-1 intercept to a degenerate boundary solution (complete separation -- every historic trap_count row decoded to state 1 had trap_count == 0 exactly, none of them anchored, once the historic period's own anchor was removed, see above) -- trap_count's pseudo-residual miscalibration remains open, unresolved by that attempt (see quarto_reports/plague_model_summary.qmd's Pseudo-residuals section). chewcard_count (binom, trials fixed at 10) and a seasonal detection formula on burrow_count's mean (ground cover/soil cracking obscure burrows differently through the year) were added the same period as separate, independent changes -- see r/d_fit_plague_hmm.R for both. Second pass: add a zone-or-subregion random effect on the transition probabilities on top of this same pooled fit -- see the earlier paragraph on AE zone's intended role. Originally attempted (2026-08 early) and parked: neither ae_zone (8 groups) nor grdc_subregion (18 groups) converged cleanly with implausible logit-scale coefficients, diagnosed at the time as sparse anchor data per group being the real constraint. That diagnosis was corrected the same broader period (2026-08): the actual cause was one specific zone, "Qld Central" -- zero plague anchors and zero real observations of any kind since 2008 (r/d_build_hmm_data.R's exclude_zones argument, added to drop it) -- not sparse data per group generally. Excluding it, every zone-augmented model tested converges cleanly: fixed interactions on both soil_moisture and rain_whiplash_trough_to_peak, and both a random intercept and a random intercept+slope on soil_moisture (the slope version's own zone deviations independently reproduce the same regional split the fixed interaction shows, but its AIC came out worse than intercept-only and it didn't add a diagnosis the other two hadn't already agreed on). plague_hmm_second_pass uses a random intercept only (~ rain_whiplash_trough_to_peak + gpp_rolling6 + soil_moisture + s(ae_zone, bs = "re")) -- see r/d_fit_plague_hmm.R's header for the full investigation and quarto_reports/plague_model_summary.qmd's "Zone-specific deviations" section for the fitted per-zone coefficients (a legible NSW-vs-SA regional split, not noise, though still built on thin per-zone anchor counts). grdc_subregion hasn't been retested since. A non-linear factor-smooth per zone (mgcv's s(<covariate>, ae_zone, bs = "fs", k = 4), each zone's own wiggly curve rather than just its own linear slope) was tried next as a richer alternative and reverted the same day -- every variant failed more decisively than the pre-Qld-Central linear attempts (lambda exploding to ~1e300 forcing the whole smooth flat while another coefficient blew out compensating; or, in the worst case, a "clean" convergence code masking an actually-degenerate fit where the two hidden states' own transition intercepts came out numerically identical). Root cause: a k=4 curve per zone per transition asks for far more shape information than ~287 plague-onset anchors can identify -- a genuine over-parameterisation relative to anchor volume, distinct from the earlier dead-zone problem. A pooled LINEAR random slope on rain_whiplash_trough_to_peak (matching soil_moisture's own random-slope treatment) was tried next as a lower-complexity alternative -- also unstable, just differently: "false convergence" with NaN standard errors and an AIC of -28792 alone (~46,000 points off every working model), and the identical-intercepts collapse again when combined with soil_moisture's own random slope. Third pass: plague_hmm_third_pass adds rain_whiplash_trough_to_peak's own zone-varying slope as a FIXED interaction instead (rain_whiplash_trough_to_peak:ae_zone, not the full "*", so it doesn't duplicate the zone intercept s(ae_zone, bs = "re") already supplies) -- converges cleanly (code 0, FE range -3.45 to 3.22, RE range -0.90 to 0.62), unlike the random-slope version. soil_moisture's own sign flip reproduces here too, independently confirming it as a robust finding across three different model specifications, not an artefact of one. See r/d_fit_plague_hmm.R's header for the full investigation and quarto_reports/plague_model_summary.qmd's "Zone-specific deviations" section for both coefficient tables (zone intercepts and rain_whiplash_trough_to_peak's own zone slopes).

Prediction-side needed a genuine design decision, not just a new function argument: min_temp's own training covariate is a true 3-month within-season mean (min_temp_seasonal_raster, season-grain layer names like "Winter-2025", incompatible with the "<month>_<year>" naming every other prediction raster depends on for r/d_predict_plague_risk.R's own shared-period logic) -- used min_temp_raster_coarse instead (full monthly grain, matching naming), a minor, accepted definitional mismatch (one raw month's value standing in for that season's own 3-month mean) since minimum temperature changes smoothly across a season, unlike rainfall or GPP. See r/d_fit_plague_hmm.R's and r/d_predict_plague_risk.R's own headers for the full detail. Prediction (r/d_predict_plague_risk.R, plague_risk_map target) applies the fitted covariate-to-transition-probability relationship to the gridded covariate surface (0.1 degree), producing a continuous risk map including un-monitored paddocks -- now from plague_hmm_fourth_pass, which needed the same genuine per-cell ae_zone value in predict_plague_risk()'s own newdata construction that plague_hmm_second_pass first required (rasterized from fit_zones_sf onto the covariate grid's own template, not a per-cell spatial join, for the same extract()-performance reasons documented elsewhere in this file), plus min_temp_raster_coarse as a fourth raster argument. Explicitly masked to the AE zones that actually have >=1 fitted paddock -- derived live from hmm_data_first_pass itself (2026-08, so it automatically tracks exclude_zones above rather than needing its own separate exclusion list) -- rather than raw state-outline polygons: AE zones are a curated grain-growing layer, so masking to them avoids extrapolating into non-agricultural parts of a fitted state (deserts, alps, cities) the same way an earlier fix avoided extrapolating into Western Australia entirely (WA has its own distinct cropping calendar, noted separately above). Uses hmmTMB's own HMM$predict(what = "tpm", newdata = ...) rather than manually re-deriving the linear predictor, mapping specifically Pr(not-plague -> plague) at the four covariate rasters' own latest SHARED period -- rain_whiplash_trough_to_peak/min_temp_raster_coarse are monthly grain but gpp_rolling_raster_6/soil_moisture_raster_coarse are trimmed to season-end months only (Feb/May/Aug/Nov), so the shared period has to be found across all four rasters' own layer sets, not just read off rain_whiplash's own latest month (2026-08, r/d_predict_plague_risk.R). The forecast is structurally one season ahead only, not a running seasonal forecast: all four covariates are built entirely from realised observations (SILO rainfall, PML/VIIRS GPP, AWRA soil moisture, SILO minimum temperature) with no forward-looking forecast/outlook component in any of them, so none can be computed past the most recently completed month of real data, and the transition formula itself always relates one season's covariates to the FOLLOWING season's state -- a longer horizon would require forecasting the covariates themselves, not a model change. Sanity-checked on real data: the highest-risk grid cells land in real grain-growing regions (South Australia's western coastline near the Eyre Peninsula, a smaller hotspot in central-east New South Wales), not ocean or artifacts.

burrow_count and trap_count both carry a search-effort offset on their nbinom2 mean (burrow_count added 2026-08, trap_count added shortly after the same period): burrow_transects_surveyed (2/4 most common, 1/3/5/6/8 also occur, up to an 8x range) and number_functional_traps_session (true trap-nights, 4-827, up to a ~200x range) both drive a proportionally higher raw count for reasons having nothing to do with density, and hmmTMB's own offset() formula term is silently dropped (confirmed by tracing its make_matrices(), which never reads mgcv::gam()'s own $offset component) -- both use log_burrow_metres_searched/log_trap_effort (r/d_build_hmm_data.R) as a genuine covariate term instead, coefficient fixed at exactly 1 via Observation$new(fixpar = ...), which reproduces true offset behaviour (fitted mean scales exactly with search effort) while leaving every other coefficient/pseudo-residual materially unchanged -- see r/d_fit_plague_hmm.R for the full mechanism. trap_count's own version was confirmed live before committing: AIC improved substantially (18347.7 -> 18007.2), trap_count.shape moved from a near-degenerate 0.057/1.05 (state1/state2) to a far more plausible 0.23/1.54, and the transition coefficients were materially unchanged -- but it did not fix trap_count's own pseudo-residual miscalibration, consistent with that being a cause shared across all three streams rather than an effort-specific problem. Adding both offsets prompted a distribution-family review for trap_count and burrow_count: trap_count is genuinely proportional data (unique individuals out of trap-nights trials), so a success-rate model (beta/zoibeta on the capped success rate, or true binom) was considered instead of a count -- true binom is ruled out for the same reason it nearly was for chewcard_count (hmmTMB's binomial trials parameter is fixed, not covariate-varying, and trap-nights' ~200x range can't be standardised the way chewcard's card count could), and beta/zoibeta turned out to be non-functional in the installed hmmTMB (v1.1.2) -- confirmed live returning a NaN log-likelihood even on a trivial constant response with no zeros or boundary values, versus a known-good family working fine under the identical harness; neither family has any documentation or example in the installed package. hnbinom (hurdle negative binomial) was also tried, as a distribution that might represent trap_count's heavy zero mass (72%) more explicitly than nbinom2 -- it works on its own, but has no parameter that is both free-to-offset and decoupled from the count's own variance the way nbinom2's mean/shape split is, so pairing it with an effort offset drove its size parameter to ~1240 at high-effort rows, at which point the hurdle math underflowed to NaN (confirmed live via a manual pdf domain check). nbinom2 remains the family for both streams -- the only one of the distributions actually usable in this hmmTMB build with a clean, numerically stable multiplicative effort offset; see r/d_fit_plague_hmm.R's header for the full investigation, including why zinbinom (tried earlier for burrow_count, z-inflation collapsed to 0) was judged redundant rather than re-tested for trap_count. chewcard_count's own varying-deployment problem (10/20/40 cards depending on 1-4 transects, standardised down to a fixed trials = 10 by only reading each session's first 10 cards, r/a_data_rapid_session_summary.R) was investigated the same way and confirmed structurally unfixable in this package, not just unexplored: mgcv's standard varying-trials mechanisms (a weights argument, or a cbind(successes, failures) response) can't reach hmmTMB's real likelihood at all -- its own use of mgcv::gam() is provably a design-matrix generator only (called with the real response replaced by a dummy constant, fit = FALSE, never actually fitting anything), while the real per-row density is a hardcoded dbinom(x, size, prob) call with size a per-state constant sourced from par(), confirmed live that giving it its own covariate formula gets silently ignored -- and beta-binomial (the natural distribution that would sidestep this by not needing a fixed trials count at all) isn't implemented anywhere in hmmTMB, checked against both the installed package and the current GitHub source directly. The first-10-cards restriction stays -- confirmed live it costs precision, not accuracy (only 13.5% of rows deploy >10 cards, and their detection rate barely differs whether all cards or just the first 10 are used) -- with a genuine block-stream alternative (cards 11-20/21-30/31-40 as extra binom(10) streams) identified but parked, needing real cross-file plumbing for a modest, uncertain gain; see r/d_fit_plague_hmm.R's header for the full detail. bait_history (recent poison-baiting -- a genuine session-level confound that would suppress all three streams at once, unlike anything else tried against the pseudo-residual problem) was plumbed through from Section A (previously dropped at build_survey_visit_grid()'s own select()) and tested the same way (2026-08): a real AIC gain (-68.7, the largest single observation-side addition tried) but parked, not adopted -- bait_history_rapid has zero confirmed-baited ("yes") rows anywhere in the fitted panel (all still too recent to clear the covariate-completeness trim, not a bait_history-specific gap) and trap_count's own 5 "yes" rows produce an opposite-sign coefficient between states, the same weak-identification signature as the reverted ~era attempt/the "Qld Central" blow-up above. Plumbing kept (confirmed a pure addition, no effect on any adopted pass); revisit once real "yes" events clear that filter. See r/d_fit_plague_hmm.R's header for the full investigation, including a resolve_survey_visits()-mode alternative (summing repeat within-season visits, sound for chewcard_count but not trap_count's own cross-session recapture identity) also considered and rejected -- baiting, like crop sowing/harvest, can genuinely happen IN BETWEEN two visits within one nominal season, so any season-level aggregation of a visit-varying field (bait_history, crop_group/crop_stage alike) risks attributing a later event backward onto an earlier visit's own response counts; mode = "first" keeps each visit-varying field paired with its own visit's counts, which is why it's the correct choice here, not just the status-quo default.

ADOPTED (2026-08): every observation-side covariate is now a deliberate choice between two states, not hmmTMB's own silent default (free per state unless fixpar'd) -- chosen on ecological grounds over AIC, since hmmTMB's own logLik.HMM() has flagged AIC as "experimental for models with random effects or splines" on every adopted model since the ae_zone random-intercept pass, so leaning on it for this design decision specifically was judged the wrong tool. The organising question per covariate: is it a DETECTION mechanism (how easy a real sign is to observe, shouldn't depend on the true state) or a DENSITY/DISPERSION mechanism (a real, potentially state-dependent ecological quantity)? Tied to one shared, freely-estimated value across both states: season (all three streams), gpp_finescale, and season:summer_zone_ne (burrow_count only) -- all three were already motivated in this project's own text as ground-cover/crop-growth-stage visibility effects, not density ones. Left free per state: ae_zone (burrow_count, and newly chewcard_count) and shape (trap_count, burrow_count) -- ae_zone's own observation-side signal echoes the same NSW-vs-SA regional split already established as a genuine outbreak-magnitude difference on the transition side, and shape (overdispersion) has no detection story to begin with. Mechanism: hmmTMB's fixpar argument supports tying coefficients to one shared ESTIMATED value (an integer/factor-level tag, distinct from fixing to a known constant, which is what the two search-effort offsets still use) -- confirmed live this has no structural scope limit, accepting a tie even across different distribution families (nbinom2 log-link, binom logit-link) with no warning, meaning a genuine shared-across-STREAMS effect (e.g. "season affects one underlying mouse density that each stream then measures its own way") is mechanically reachable but not scale-aware -- parked as a materially bigger undertaking (a real shared continuous latent-density layer) rather than attempted via a naive cross-family tie. ae_zone was also tested as a new addition to chewcard_count.prob (adopted -- comparable data volume to burrow_count, plausible coefficients) and to trap_count.mean as a random effect (not adopted -- confirmed live as a genuine data-volume ceiling, not a specification problem: state 2's own lambda exploded to ~2.3e10, collapsing every zone deviation to ~0, because trap_count's own zone x state cells are far thinner than burrow_count's ever were, e.g. NSW NE Qld SE 484 state-1 rows vs 3 state-2, SA Vic Bordertown-Wimmera 0 rows in EITHER state -- a real coverage gap, the same shape of problem "Qld Central" was excluded from the whole panel for, just stream-specific here). Confirmed live before adopting: the full spec (this tying scheme plus chewcard_count's new ae_zone) has a slightly BETTER AIC than the original all-free baseline (17530.3 vs 17554.9) despite the real cost of tying in isolation, because chewcard_count's own gain more than offsets it -- a reassuring cross-check, not the basis for the decision. Pseudo-residuals stayed essentially unchanged throughout every variant tested here, consistent with this whole design axis being orthogonal to that still-unresolved problem. chewcard_count's own varying-deployment problem (10/20/40 cards depending on 1-4 transects, previously handled by truncating every survey down to a fixed trials = 10, see above) was revisited and given a genuine effort-aware fix (2026-08, ADOPTED): checked hmmTMB's own documentation first (per this file's own instruction to consult the package's help pages) and confirmed there's no separate "occupancy modelling" API -- its case_studies/crossbill_occupancy.R is a completely standard 2-state HMM built from the exact same MarkovChain/Observation classes already used here. What it DOES confirm: hmmTMB's own canonical fix for a varying number of replicates is multiple FIXED-size binom streams, one per distinct replicate count, NA elsewhere -- validating the block-stream idea already parked above as the package author's own documented pattern, not a workaround. Implemented and tested live against a collapsed "any card chewed" alternative (a single Bernoulli/binom(1) stream using ALL deployed cards, trading the graded count's own information for robustness to within-transect card correlation a plain binomial can't otherwise absorb -- beta-binomial, the natural fix for that kind of extra-binomial variance, is confirmed absent from hmmTMB, same finding as above): the block-stream version (chewcard_count + new chewcard_block2/3/4 streams for cards 11-20/21-30/31-40, every coefficient tied across all four blocks -- same underlying detection-rate model, not four independent ones -- season also tied across states, ae_zone free across states, matching the treatment above) converged cleanly; the collapsed yes/no version did not ("false convergence", NA/NaN function evaluations) -- a single Bernoulli trial gives the optimiser far less room than binom(10) did, so the same ae_zone x state sparsity that produced burrow_count's own NSW NW Qld SW blow-up (12 all-zero rows) bites far more easily with only 1 trial per row, a genuine, informative negative result. ADOPTED the block-stream version. This workflow is based on function-orientated programming, where each function generally acheives one task. 
The priority is therefore on readability, even if it requires more code. It is important all code is explained using hashed comments. 
Each script should be named the same as the function name, except with a prefix of "a_", "b_", "c_" or "d_" corresponding to which major pipeline section it is used in (matching the "A)"/"B)"/"C)"/"D)" section headers in _targets.R). 


AI assistants should read every .R file.
AI assistants should never commit or push the "docs/" folder to GitHub -- it deploys straight to the public GitHub Pages website, so updates to it are pushed manually/deliberately, not swept up into an ordinary commit.
AI assistants should always explain created code using comments.
AI assistants should put new functions at the top of the r script, although AI assistants should generally not define functions inside of functions unless they are very brief, anonymous functions. 
AI assistants should ensure all created quarto documents are self-contained. 
In "_targets.R", keep comments terse: one short sentence per line, not a wrapped paragraph spanning several "#" lines. Detailed rationale (why a function works the way it does, edge cases, etc.) belongs in that function's own header comment in "r/", not duplicated in "_targets.R" -- "_targets.R" comments should just say what a target does and point to the relevant function for detail.
Within each major section ("A)"/"B)"/"C)"/"D)"), subdivide with numbered "1)", "2)", "3)"... subheadings, and within those, lettered "i.", "ii.", "iii."... sub-subheadings where a further split is useful -- matching section A's existing style.
Blank lines around these headings (any level -- "A)", "1)", "i."): one blank line between a heading and its own first sub-heading/target (introducing its children); two blank lines between the end of one heading's content and the next heading of any level (a sibling, or a step back up).
In "_targets.R", a target's call collapses onto one line if it has 3 or fewer arguments (counting whichever call -- the tar_file()/tar_terra_rast() wrapper or the function it wraps -- actually carries the meaningful configuration); with 4+ arguments, give each its own line with the "=" signs vertically aligned. A pipe chain ("|>") always gets one step per line regardless of argument counts. An inline "{ }" block keeps the opening brace on the assignment's own line, indents the body one level, one statement per line, and closes with "}" back at the target's own indentation.
